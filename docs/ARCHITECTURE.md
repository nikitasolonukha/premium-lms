# Архитектура

## Границы приложения

Модульный монолит: App Router отвечает за страницы и same-origin HTTP, `src/lib/actions` — за команды, `src/lib/server` — за пользовательский доступ к данным, сессии и привилегированные операции. Типизированные доменные правила и схемы находятся в `src/lib`. PostgreSQL — окончательная граница полномочий и целостности.

Next.js 16.3.7, React 19.3.0, TypeScript, Node 22+, Tailwind, Manrope с кириллицей. Доступные диалоги построены на Radix primitives в стиле shadcn/ui. TipTap загружается отдельным динамическим чанком; dnd-kit поддерживает pointer и keyboard. Авторизационные формы используют React Hook Form. Zod проверяет команды; JSON Schema-снимки дополнительно проверяются расширением `pg_jsonschema` внутри SQL RPC.

Браузер не получает Supabase client, refresh token в JavaScript или service key. Сервер создаёт клиент от имени пользователя, читает HttpOnly-cookie и выполняет обычные запросы с RLS. Исключения с service key: счётчики входа, подготовка/проверка загрузок, короткие разрешения на материалы, публичный логотип/иконка из узкого RPC, приглашение Student. Они собраны в явно серверных файлах.

## Модель контента

`courses`, `modules`, `lessons` — постоянные идентификаторы. `course_revisions`, `module_revisions`, `lesson_revisions`, `lesson_blocks` — состав редакции. Курс указывает на `published_revision_id` и опциональный `draft_revision_id`. При первом сохранении после публикации создаётся новая редакция. Сохранение черновика заменяет только её состав в одной транзакции.

`version` обеспечивает optimistic concurrency: изменение из устаревшей вкладки получает конфликт. BroadcastChannel предупреждает о сохранении в соседней вкладке. Автосохранение сохраняет снимок, учитывает последующие изменения и не снимает dirty-флаг преждевременно. Публикация ожидает сохранения актуального документа, проверяет его состав и атомарно меняет указатель опубликованной редакции.

Ученик не читает черновик или блоки исключённого из публикации урока. В последовательном режиме программа показывает названия закрытых уроков, а SQL-проверка доступности исключает блоки, медиа, playback и команды прогресса. Завершённые уроки остаются доступными при перестановке.

Все 11 блоков имеют `id`, `version`, `type`, `data`; порядок хранится в нормализованной таблице. Типы: heading, rich_text, image, video, file, link, quote, callout, divider, code, gallery. Rich text рендерится React-элементами по списку разрешённых типов/атрибутов, без произвольного HTML.

## Доступ и обучение

Прогресс курса возвращает `course_progress(cid)` как ограниченный выбранным курсом JSON, поэтому REST max_rows=200 не обрезает завершения больших программ. Процент округляется вниз: 299 из 300 — 99%, 100% только при полном завершении. Каталог, dashboard и страница курса используют одинаковый смысл завершения.

RLS-предикаты чтения редакций вычисляют набор разрешённых revision IDs один раз на SQL statement через стабильную `private.readable_revisions()`. Эта оптимизация не отключает RLS и не добавляет service-role чтения. После неё прямые проверки Student A/B, MFA staff, отзывов и скрытых черновиков повторяются. В локальном QA полный прогресс и каталог для 300 уроков прочитаны за 189 мс: [последний замер](qa/evidence/scale-progress.json). Это измерение на данном хосте, не нагрузочный SLA.

`enrollments(user_id,course_id)` уникален. `access_grants` хранит основание, срок и отзыв; manual не смешивается с будущими purchase/subscription/organization. Доступ registered открыт подтверждённым аккаунтам; restricted требует действующего основания. Роли хранятся отдельно в `user_roles`, не в metadata профиля.

`progress(user_id,lesson_id)` уникален: открытие, последнее открытие, завершение и позиция видео. Завершение идемпотентно; редактирование/перестановка сохраняют историю. Процент использует текущий опубликованный состав. `learning_activity` фиксирует отдельные дни посещений, чтобы график за 30 дней не терял прошлые визиты.

Сохранённое фильтруется RLS заново; отзыв доступа скрывает результат, но сохраняет историю для возможного восстановления. Дублирование курса создаёт новые идентификаторы структуры и не копирует назначения/прогресс. Курс удаляется логически. Slug-алиасы сохраняют старые адреса; простое изменение названия не меняет URL.

## Запросы и производительность

Server Components вызывают серверный DAL. Каталог возвращает по 12 карточек; пользователи, уроки поиска и библиотека — по 20; аудит — по 30. Фильтры живут в URL. Поиск использует PostgreSQL FTS для русского/английского и поиск фрагмента названия. RLS и условия доступа применяются до пагинации и total.

Поиск/сохранённые уроки агрегируются одним RPC, без отдельного запроса на каждый курс. Каталог считает метрики в одном SQL-запросе. В больших пользовательских списках выбор курса имеет собственный поиск и пагинацию. Тяжёлый редактор не включается в ученические страницы. Изображения подготавливаются Sharp до 1800 px и выдаются приватно, без общего Next Image cache.

## Медиа

`media` хранит owner, purpose, ожидаемые метаданные, статус pending/ready/rejected/deleted и hash. `block_assets` связывает объект с конкретной редакцией и блоком. Загрузка получает разрешение только на выделенный object key, без overwrite. Финализация проверяет сигнатуру, размер, архивную структуру и декодирование изображений. Учебный объект становится доступен лишь после `ready` и ссылки из доступного опубликованного контента.

Изображения: сервер проверяет права и выдаёт Storage signed URL до 300 секунд. Скачивание: 60-секундный HMAC grant на конкретный asset; конечный маршрут проверяет срок, запрашивает короткую Storage-ссылку и стримит ответ с RFC 5987 `filename*` для кириллицы. Уже выданное разрешение действует до TTL; новое после отзыва не выдаётся.

## Расширения

`VideoProviderAdapter` / `PlaybackGrant` описывают источник, возможности, защищённость и срок. YouTube, Vimeo, Rutube, direct и allowlisted embed реализованы. Mux/Cloudflare возвращают явное состояние «не подключён», отсутствуют в выборе CMS. Для них требуется серверная реализация подписи playback после той же проверки доступа и отдельный integration QA.

Будущие платежи должны создавать отдельные `access_grants` через идемпотентный webhook; они не должны менять роль. Организации добавляют tenant и membership с отдельным RLS-аудитом. Drip расширяет централизованную доступность урока. Задания/экзамены/сертификаты ссылаются на постоянный lesson/course ID, а версия задания должна сохраняться с ответом. SSO интегрируется с Auth, не заменяя DB RBAC. DRM требует подходящего видеопровайдера и лицензирования; watermark им не является.
